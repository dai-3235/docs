The earlier posts described the ideas: [why a semantic layer exists](../why-a-semantic-layer-exists/), [how business names bind to storage](../logical-versus-physical-model/), and [how the joins are chosen](../finding-the-join/). This post puts those ideas inside a running service. It follows one request from the moment it arrives to the moment a single result goes back, and then covers the parts that make it operable: several SQL engines, caching, feature flags and testing.

It is also written to be usable as a worked answer to a system design question. The structure, the trade-offs and the things to leave out are the point.

## The pipeline

A request moves through seven stages. Each stage either passes its output to the next or stops the request with a typed reason. Select a step, or press Play, to walk through it.

<Workflow client:visible flow={platformFlow} title="Request to merged result" height={420} />

1. **Parse.** The request is validated against the shape the gateway accepts. A malformed request is refused here, before any metadata is read.
2. **Resolve.** Logical metrics and dimensions are matched to physical bindings by priority, and the grain rule is applied. This is where an ambiguous metric or a breakdown that is too fine is refused.
3. **Split.** Metrics held in different databases are separated into parts, each of which stays inside one database. A selection that would need a join across databases is refused with its own reason.
4. **Plan joins.** Each part gets its route from the cost-ordered search, under the hop limit and the strategy ladder.
5. **Generate SQL.** Each part is rendered in the dialect of the engine that holds its data.
6. **Execute.** Parts run against their engines, in parallel where they are independent.
7. **Merge.** Part results are combined on the shared breakdowns into one result.

Splitting and merging deserve a note. A request for two metrics that live in different databases cannot be a single query. It can be two queries that share a breakdown, for example both grouped by advertiser, whose results are then combined by that breakdown. That works for measures. It does not work for a join between tables in different databases, which is why that case is refused and not attempted.

## One stage, one contract

The stages share a small contract: take the output of the previous stage and return either a value or a typed reason.

```ts
type Outcome<T> = { ok: true; value: T } | { ok: false; reason: FailureReason }

interface Stage<In, Out> {
  name: string
  run(input: In): Promise<Outcome<Out>>
}

async function runPipeline<In, Out>(stages: Stage<unknown, unknown>[], input: In): Promise<Outcome<Out>> {
  let current: unknown = input
  for (const stage of stages) {
    const outcome = await stage.run(current)
    if (!outcome.ok) return outcome
    current = outcome.value
  }
  return { ok: true, value: current as Out }
}
```

Two properties come from this shape. A failure always carries the same typed reason that the earlier posts described, so a client handles every stage's failures the same way. And each stage can be tested alone, with plain values in and out.

## Several SQL engines

One gateway usually fronts more than one kind of engine: a columnar analytics store for large facts, a row store for small dimensions, a lakehouse for history. A JVM service talks to them over a common driver interface, and the part that differs between them is the dialect.

The dialect layer is a small interface, not a template engine.

```ts
interface Dialect {
  quote(identifier: string): string
  limit(sql: string, rows: number): string
  truncateToDay(expression: string): string
  castToText(expression: string): string
}

function renderSelect(dialect: Dialect, table: string, column: string, rows: number): string {
  const body = `SELECT ${dialect.quote(column)} FROM ${dialect.quote(table)}`
  return dialect.limit(body, rows)
}
```

The trade-offs are real. A common driver interface hides the transport and not the behavior: types, null handling, timeouts and how an engine reports cancellation still differ. A dialect layer keeps generated SQL correct but cannot make a slow engine fast, so the planner needs to know which engine a part targets. And each new engine adds a dialect to maintain and a set of behaviors to test. Add engines when a real need is in front of you, not before.

## Caching

Caching sits at two categories of place.

- **Metadata.** Metrics, dimensions, bindings, join rules and virtual tables are read often and change rarely. They are held in memory and reloaded when the data changes, so a change takes effect without a deploy.
- **Results.** A part's result can be cached against a key built from what the part asks for: the physical metrics, the breakdowns, the filters and the engine. Anything that changes the answer must be in the key.

```ts
interface PartRequest {
  engine: string
  metrics: string[]
  breakdowns: string[]
  filters: Record<string, string[]>
}

function cacheKey(part: PartRequest): string {
  const filters = Object.keys(part.filters)
    .sort()
    .map((name) => `${name}=${[...part.filters[name]].sort().join(',')}`)
  return [part.engine, [...part.metrics].sort(), [...part.breakdowns].sort(), filters].join('|')
}
```

Sorting makes two requests that mean the same thing share a key. The danger is the opposite one: a key that leaves out something that changes the result will serve a wrong answer from the cache, and the user will not know. Result caches also need an expiry that matches how fresh the underlying data is allowed to be, and a way to bypass them when someone is investigating a number.

## Feature flags

A gateway like this changes behavior in risky places: a new route-finding rule, a new dialect, a new cache. Feature flags let each change be switched on for a narrow slice of requests and off again without a deploy. Keep the flags few and short-lived. A flag that outlives its rollout becomes a second configuration system that nobody owns.

A flag should change which code path runs, never what a metric means. Definitions belong in the metadata, where they are reviewed.

## Limits, timeouts and partial failure

Every call to an engine has a timeout, a bounded number of retries with backoff, and a defined outcome when it still fails. The outcome matters most when a request was split. If one part times out, the gateway can either fail the whole request or return the parts that succeeded with a clear marker that the rest is missing. Which one is right depends on the consumer, so make it a declared choice per request type, and never let a partial result look like a complete one.

Each engine also gets its own concurrency limit. Without one, a slow engine fills the service with waiting parts and starves requests that never touch it.

## Explaining an answer

A result carries more than rows. It carries the physical metrics chosen, the route used for each part and which rung of the strategy ladder produced it. That record is what lets someone answer "why did this number come from that table" without reading the code, and it is what a dashboard of refusals is built from: counting the typed reasons shows which part of the model is thin.

## Testing the platform

The gateway is tested through what it does, not how it is built. A test sends a request and checks the result or the typed reason, against a small model with real, tiny engines where that is cheap.

- **Resolving.** Given a model and a request, the right physical metric is chosen, or the right reason is returned.
- **Routes.** A table of cases, in the spirit of the demo scenarios, checks which route is chosen and why.
- **Dialects.** The same plan renders to each engine, and each rendering runs against that engine and returns the same rows.
- **Failures.** Every typed reason has a test that produces it.

Tests of this kind survive refactoring, because they never mention a private helper. They also double as documentation: a failing case is a sentence about what the gateway should do.

## Pros and cons

| | Advantage | Cost |
|---|---|---|
| Staged pipeline | Each stage is small, testable and returns a typed reason | More boundaries to keep consistent |
| Split and merge | Metrics in different databases can be answered together | Merge rules must be exact, and some requests are still refused |
| Dialect layer | Generated SQL is correct per engine | One more thing to maintain per engine |
| Metadata cache | Changes apply without a deploy | Reloads need care so a bad record never half-applies |
| Result cache | Repeated requests are cheap | A wrong key serves wrong answers |
| Feature flags | Risky changes roll out and back safely | Stale flags become hidden configuration |
| Behavior tests | They survive refactoring | They need small real engines to be convincing |

## When not to build this

- **A single engine and a modest set of reports.** A well-chosen modeling tool, or a set of reviewed saved queries in the database, does the job with far less machinery.
- **No platform team.** A gateway is a service with an on-call burden. Without people to run it, its failures land on the consumers it was meant to protect.
- **Latency-critical serving.** The layers add work to every request. If answers must come back as fast as a direct query, serve those from a purpose-built store.
- **Metrics that are still being invented.** Governing definitions before the business agrees on them just records the disagreement.

## What it costs

The honest cost is the surface area. Every stage, engine, cache and flag is something that can fail in its own way, and the typed reasons are only useful if each failure is mapped to one. Start with a thin pipeline, a single engine and a metadata cache, and add the rest when a concrete need pays for it.
