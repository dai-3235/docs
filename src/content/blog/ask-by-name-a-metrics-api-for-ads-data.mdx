The datasets already exist. Event logs, clicks, conversions, spend and billing all land in a warehouse. The problem is not storage. It is that every dashboard, export, notebook and service writes its own SQL against them, so the same number, say impressions last week, comes out three different ways.

The fix is small to state: **one central service that owns the definition of every metric and dimension, and exposes a dynamic API that consumers query by business name.** This post is the whole design, kept as lean as I can keep it, with the scale decisions left until they are earned.

The examples use an invented ad-reporting domain. Table names are made up, and nothing here describes a particular company's system.

## What problem are we solving

Four things go wrong when each consumer talks to the tables directly.

- **Different answers.** Each team joins and filters in its own way, so the same metric has several values.
- **Hidden rules.** Which table to use, which join is safe, which rows to exclude: all of it lives in people's heads or in copied queries.
- **Slow change.** A new breakdown needs a new query for each consumer. A table move breaks all of them.
- **No guardrails.** Anyone can join a fact table to itself through a many-to-many table and double-count spend.

A central service fixes all four by giving consumers one question to ask: *which metrics, broken down by what, filtered how, over which dates.* The service answers it, and the SQL stays an implementation detail.

## The shape: one gateway, four tiers of query

A request names metrics, breakdowns, a filter and a time range. The gateway turns it into SQL, runs it on a registered datasource, and returns rows. Everything else is a question of how much work that translation does.

| Tier | What the consumer sends | What the gateway does | Needs |
|---|---|---|---|
| 1. Simple aggregation | metrics + breakdowns on one table | pick the table, `GROUP BY` | metadata only |
| 2. Rich join query | metrics + breakdowns that live on different tables | find the join route, join, aggregate | join rules |
| 3. Derived metrics | ratios and differences of base metrics | compute from base metrics after aggregating | metric formulas |
| 4. Template query | a named query with parameters | render a reviewed CTE template, run it | a template in the repo |

## Organize the metrics once

Consumers should never see column names. They see two registries, written as data and editable without a deploy.

- A **logical metric** is a business name with a meaning: `impressions`, `spend`, `ctr`. A **logical dimension** is a business name for a way to slice: `promotion`, `device`, `day`.
- A **physical metric** binds a logical metric to a column of one table, with an aggregation and a priority. A **physical dimension** binds a logical dimension to a column of a table.

```ts
interface PhysicalMetric {
  logicalMetric: string
  table: string
  column: string
  aggregation: 'sum' | 'count_distinct'
  priority: number
}

const impressionsOnDaily: PhysicalMetric = {
  logicalMetric: 'impressions',
  table: 'ad_event_daily',
  column: 'impressions',
  aggregation: 'sum',
  priority: 10,
}
```

Two ideas do most of the work.

**Grain.** Tables and dimensions sit on an ordered scale from fine to coarse: event, placement, promotion, sponsor. A table can be broken down only by dimensions at its own grain or coarser. A daily promotion table cannot give you a per-banner breakdown, and the gateway says so instead of guessing.

**Priority.** One logical metric can have several physical homes, for example an hourly table and a daily rollup. The gateway picks the cheapest table that can answer the whole request, and refuses with a typed reason when two tables tie. A refusal such as `ambiguous_metric` or `no_join_route` is far easier to live with than a silently wrong number.

Because the datasets are already there, onboarding is registration, not migration: add the table, bind its columns, declare its grain, and it becomes queryable.

## Join rules and route search

This is the part of the gateway that causes the most surprising bugs, so it gets the most space. The question is narrow: a request needs a metric from table A and a dimension from table B. Which joins connect them, and which of the possible routes is the right one?

### Define the rule, not the route

Nobody writes routes. Metadata owners write **join rules**, one per real relationship between two tables, and the gateway finds routes by searching the graph those rules form.

```ts
interface JoinRule {
  id: string
  from: string
  to: string
  fromRole?: string
  toRole?: string
  cost: number
  cardinality: 'one-to-one' | 'many-to-one' | 'one-to-many' | 'many-to-many'
  enabled: boolean
}
```

Each part earns its place:

- **`from`, `to`, and the join columns.** A rule is stored once. The search can walk it in either direction, so there is no need to declare a reverse rule.
- **`cardinality`** is stated from `from` to `to`. It is the only thing that tells the search whether a join multiplies rows. It is declared by the person who knows the data, because it cannot be inferred from column names.
- **`cost`** is the owner's judgment of how much to trust the join. It is not a measurement. A convention that works: `1` for a key lookup into a dimension (`many-to-one`), higher for a shortcut that skips a level, and highest for a bridge table that fans out. Price a shortcut on purpose: below the chain it skips if you trust its join columns, above it if you do not. The search follows the price without exception.
- **`enabled`** turns a rule off without deleting it. A suspect join can be switched off while the data is checked, and routes re-form around it.
- **`fromRole` and `toRole`** name the capacity in which a table takes part, so the same table can be joined twice. A sponsor table that links to a partner table twice, once as buyer and once as biller, is two rules with two roles.

Rules are validated when they are registered, not when they are used: both tables exist, the id is unique, the cost is positive, the cardinality is one of the four values. A cost of zero or less is rejected, and the next section shows why that matters.

### Why not just count joins

The first idea is breadth-first search from the metric table. It finds the route with the fewest joins and stops. Fewest joins is not safest.

Suppose an event table reaches a sponsor dimension two ways: a direct shortcut, and a chain of two clean `many-to-one` lookups. Breadth-first search takes the shortcut. If the shortcut goes through a `many-to-many` bridge, each event row now appears once per matching bridge row, and spend is counted several times. The result looks plausible, and nothing fails.

What the search needs to minimize is not the number of joins but the **risk** of the route. That is what the cost and the cardinality are for.

### Several ways to join, one chosen

Take a concrete request: total `spend` by `sponsor`. The metric lives on `ad_event_fact`, the dimension on `sponsor_dim`. The model has three ways to get there.

<Workflow client:visible flow={routeChoiceFlow} title="Three ways from an event to a sponsor" height={400} />

Each route is scored by adding up its joins. A join contributes its declared cost, one fan-out if it multiplies rows in the direction walked, and one join.

| Route | Joins | Sum of costs | Fan-outs |
|---|---|---|---|
| A. shortcut | 1 | 2.5 | 0 |
| B. event, placement, promotion, sponsor | 3 | 1 + 1 + 1 = 3 | 0 |
| C. through the banner rotation | 4 | 1 + 3 + 1 + 1 = 6 | 1 |

The gateway picks the route with the lowest tuple of (cost, fan-outs, joins). Here that is A, at cost 2.5. Fewest joins also picks A, so far they agree.

Now the owner learns the shortcut's join columns are only approximately right, and raises its cost from 2.5 to 4. Nothing else changes.

| Route | Joins | Sum of costs | Fan-outs | Picked by fewest joins | Picked by lowest cost |
|---|---|---|---|---|---|
| A. shortcut | 1 | 4 | 0 | yes | no |
| B. chain | 3 | 3 | 0 | no | **yes** |
| C. banner rotation | 4 | 6 | 1 | no | no |

Fewest joins still takes A, because it only counts joins. Lowest cost takes B, because the owner said A is worth more than B, and the search believes the owner. C loses in both cases: it costs the most and fans out, and the spend would be counted once per matching banner.

One more case, from the demo below. Two routes cost the same, 2 each. One goes through the event table and fans out on the way, the other uses a direct rule that does not. Cost ties, so fan-outs decide, and the direct rule wins. Joins only decide when cost and fan-outs both tie.

That is the whole selection rule, and it is small enough to show completely.

```ts
interface Score {
  cost: number
  fanOuts: number
  joins: number
}

function stepScore(rule: JoinRule, direction: 'forward' | 'backward'): Score {
  return {
    cost: rule.cost,
    fanOuts: causesFanOut(rule, direction) ? 1 : 0,
    joins: 1,
  }
}

function addScores(a: Score, b: Score): Score {
  return { cost: a.cost + b.cost, fanOuts: a.fanOuts + b.fanOuts, joins: a.joins + b.joins }
}

function compareScores(a: Score, b: Score): number {
  return a.cost - b.cost || a.fanOuts - b.fanOuts || a.joins - b.joins
}
```

A negative result means `a` is the better route. Everything else in the search is about finding the lowest score without listing every route.

### Why not list every route and sort

Listing all routes works on a graph this size and fails on a real one. The number of simple routes between two tables grows exponentially with the number of rules, and the hop limit only caps their length. The search avoids the listing by exploring routes in score order, so it stops at the best one.

### The search is Dijkstra with a three-part cost

Choosing the cheapest route over weighted connections is the shortest-path problem, and Dijkstra's algorithm solves it: always expand the cheapest unexpanded state, and the first time you pop the target, that route is optimal.

The twist is that "cheapest" here has three parts, compared in order:

1. **total declared cost**
2. **number of fan-outs**, joins that multiply rows (a rule walked against its cardinality: forward on `one-to-many`, backward on `many-to-one`, and either way on `many-to-many`)
3. **number of joins**

A tuple compared lexicographically still works with Dijkstra, as long as each part is added along the route and never goes negative. Adding a hop can never make the tuple smaller, so the first pop of the target is the best. That is also why a zero or negative cost is rejected at registration: it breaks the guarantee.

Order matters. Cost first means a cheap fan-out can still beat an expensive clean route, and that is a deliberate choice: costs are the owner's statement about trust, and the fan-out count only breaks ties between routes the owner priced equally. Put fan-out first if you would rather refuse any multiplying join when a clean one exists, and accept that you will pay for it in cost.

Here is the real trace for the example above, with the shortcut priced at 4. The frontier is a priority queue of partial routes ordered by score, and each step takes the best one off the front.

| Pop | Partial route | Cost | Fan-outs | Joins | What happens |
|---|---|---|---|---|---|
| 1 | start at `ad_event_fact` | 0 | 0 | 0 | push each neighbour: placement, surface, banner at 1, sponsor via the shortcut at 4 |
| 2 | `placement_dim` | 1 | 0 | 1 | push promotion at 2, the way back to the event table at 2, and banner through the rotation at 4 |
| 3 | `surface_dim` | 1 | 0 | 1 | nothing new, only a way back to the event table |
| 4 | `banner_dim` | 1 | 0 | 1 | push the way back to the event table at 2 and placement through the rotation at 4 |
| 5 | `promotion_dim` via placement | 2 | 0 | 2 | push `sponsor_dim` at 3 |
| 6 to 8 | back to `ad_event_fact` | 2 | 1 | 2 | skipped: the event table is already settled with fewer joins |
| 9 | `sponsor_dim` via the chain | 3 | 0 | 3 | **target popped, return the chain** |

Three things to notice.

- **The shortcut is never expanded.** It sits in the frontier at cost 4 when the chain pops at cost 3. Every route still in the frontier costs at least 3, and costs only grow as joins are added, so none can beat the chain. That is the proof, and it is the whole reason the first pop of the target is optimal.
- **The rotation route is never expanded.** It enters the frontier at cost 4 and the chain finishes at 3 first.
- **Turning back is skipped, not forbidden.** Pops 6 to 8 are routes that walk back to where they started. They carry a fan-out and the table is already settled, so the search drops them. Without that check every cycle would be walked again until the hop limit.

With the shortcut priced at 2.5 the same search pops the shortcut at step 9 with cost 2.5, before the chain finishes at 3. Same code, same graph, different price, different answer, and no branch in the algorithm that mentions either.

### The hop limit, and why the state has two parts

Every route is bounded by a hop limit, so a missing rule cannot turn into a walk across the whole graph. A limit sounds harmless, but it changes the algorithm. The cheapest way to reach a table can use up the hops you need to go on from there, while a costlier way with fewer hops can still reach the target. Plain Dijkstra keeps only one best label per table and would lose that second route.

So a state is `(table, role)`, and the search keeps a table's label only when it reaches the table in **fewer hops than any label already settled there**. Labels pop in order of cost, so every earlier label is at least as cheap and at least as clean. A later one earns its place only by having more hops left. This is the standard label-setting treatment of a resource-constrained shortest path, and since each table can hold at most one label per hop count, the work stays bounded by the hop limit.

Roles belong to the state for the same reason: `partner` as buyer and `partner` as biller are different nodes, so reaching the table a second time under another role is not a cycle.

### The code

```ts
function findRoute(rules: JoinRule[], from: string, to: string, hopLimit = 8) {
  const index = buildIndex(rules)
  const frontier = new MinHeap<State>(compareStates)
  frontier.push({ table: from, role: 'default', cost: 0, fanOuts: 0, hops: [] })
  const settledHops = new Map<string, number[]>()

  while (frontier.size > 0) {
    const state = frontier.pop()
    if (state.table === to) return state

    const key = `${state.table}|${state.role}`
    const settled = settledHops.get(key) ?? []
    if (settled.some((hops) => hops <= state.hops.length)) continue
    settled.push(state.hops.length)
    settledHops.set(key, settled)

    if (state.hops.length >= hopLimit) continue

    for (const step of index.get(state.table) ?? []) {
      if (step.requiredRole && step.requiredRole !== state.role) continue
      frontier.push({
        table: step.table,
        role: step.role,
        cost: state.cost + step.rule.cost,
        fanOuts: state.fanOuts + (causesFanOut(step.rule, step.direction) ? 1 : 0),
        hops: [...state.hops, step],
      })
    }
  }
  return null
}

const compareStates = (a: State, b: State) =>
  a.cost - b.cost || a.fanOuts - b.fanOuts || a.hops.length - b.hops.length
```

Two details carry the performance. The rules are indexed by table once (`buildIndex`), so expanding a state looks at that table's rules instead of scanning all of them. And the frontier is a binary heap, so taking the next cheapest state costs `O(log n)` instead of a scan.

### What it costs

For a graph of `T` tables and `R` rules, building the index is `O(R)`. A search keeps at most `H` labels per table, where `H` is the hop limit, and each label expands that table's rules, so the worst case is on the order of `H · R · log(H · R)`. That bound is loose. Because the search stops when the target is first popped, it only explores the region cheaper than the answer.

The numbers below are measured, but on a toy: the implementation from this post, synthetic random graphs, a hop limit of 8, 300 random table pairs per size, one laptop, Node. Rules get random costs from 1 to 3 and random cardinalities, so the graphs are denser and messier than a curated model. They show the shape of the cost, not a promise.

| Tables | Rules | Fewest joins, median | Cost-ordered, median | Cost-ordered, p99 |
|---|---|---|---|---|
| 50 | 122 | 6 µs | 17 µs | 150 µs |
| 200 | 498 | 22 µs | 58 µs | 246 µs |
| 1,000 | 2,499 | 113 µs | 379 µs | 1.4 ms |
| 5,000 | 12,498 | 1.0 ms | 3.2 ms | 16.5 ms |

Reading it:

- **The cost-ordered search is about three times slower than breadth-first**, which is the price of a heap and three-part comparison. Both are tiny next to the query itself.
- **A real ad model has tens to low hundreds of tables**, which is the first two rows: tens of microseconds. Planning is never the bottleneck. The warehouse query it produces takes thousands of times longer.
- **Building the index takes 0.8 ms at the large end** (12,498 rules), so build it once when metadata reloads and share it across requests. Building it inside every search makes the median 4.1 ms instead of 3.2.
- **Routes are deterministic for a given rule set**, so they cache well. Key the cache on `(from, to, rule-set version)` and the search runs once per pair per metadata reload.

The same run counts how often the cost-ordered route differs from the fewest-joins route, and how often fewest-joins picks a route with more fan-outs. On these random graphs the routes differ for 38% to 61% of pairs, and fewest-joins picks the route with more fan-outs for 15% to 23%. Do not read those as rates for real data, since the costs and cardinalities are random. They show that the two goals diverge often enough that the choice is not cosmetic. The script is `scripts/bench-route-finding.mjs` in the repository, and you can run it with `npm run bench:routes`.

### The strategy ladder

Searching is one way to find a route. A gateway can try several in order, most explicit first:

1. an explicit rule for a dimension on that table
2. a declared multi-hop route written by the metadata owner
3. a rule over several columns
4. a join inferred from a shared dimension

The principle is that explicit beats inferred. The further down the ladder, the more the system guesses and the more it has to explain, so the last rung is optional and is the first one to leave out if you are unsure.

### Alternatives, and what I would pick

The cost-ordered search is not the only way. Here is how the others compare for this problem.

| Approach | How it picks | Good at | Falls short |
|---|---|---|---|
| Fewest joins (BFS) | breadth-first from the metric table | trivial to build and explain | ignores fan-out and trust, picks risky shortcuts |
| **Cost-ordered search (this post)** | Dijkstra over declared cost, then fan-out, then joins | safe by default, fast, deterministic, explains itself | costs are human judgment and need review |
| A* | Dijkstra plus a distance estimate toward the target | big road-map graphs | no useful estimate exists between tables, and the graph is small enough not to need one |
| Explicit join paths | the author writes the route, as Cube does in its views | fully predictable, no search | authoring cost per path, stale when tables change |
| Spanning tree or star schema | design the graph so only one path exists | no ambiguity by construction | forbids models with two natural routes, such as two partner roles |
| Precomputed all-pairs routes | run the search for every pair at load time | lookup at request time | the roles and hop limit multiply the table, and caching on demand gets the same result |
| Costs learned from query history | tune weights from reviewed queries | adapts without hand-tuning | needs a trusted history, and can lock in old mistakes |

Three refinements are worth the effort before any of those:

- **Detect ties instead of breaking them.** When the two best routes have the same cost, fan-outs and joins, the request is genuinely ambiguous, and the right answer is a typed refusal that names both routes, the same as for an ambiguous metric. Run the search for the second-best route (Yen's algorithm for the k shortest routes gives it) and compare. The code above returns whichever tied route was found first, which is fine for a demo and a poor default for a service.
- **Route several dimensions as one tree.** A request with three breakdowns needs a route to three tables. Finding the cheapest set of joins that reaches all of them is the Steiner tree problem, which is NP-hard in general. The practical approach is to run the search once per dimension, merge the routes so shared joins appear once, and accept that the result is good, not provably optimal. With graphs this small, that is not a problem.
- **Remove fan-out in the query, not only in the route.** The search prefers routes that do not multiply rows, but sometimes the only route does. The query generator then aggregates each fact table to the join key in its own CTE before joining, so a row can no longer be counted twice. Looker takes the other way, correcting the sum after the fact with symmetric aggregates. Route preference and pre-aggregation work together: one avoids the hazard, the other makes the unavoidable case safe.

My pick for a lean service is the cost-ordered search with registration-time validation, tie detection and CTE pre-aggregation, explicit multi-hop routes as the escape for any case where the owner wants control, and no learned weights or inference until the simpler pieces show a gap.

## Derived metrics

A ratio is not a metric you can sum. Click-through rate computed per day and then averaged is not the click-through rate of the week. So derived metrics are defined over base metrics and computed after aggregation.

```ts
const derivedMetrics = {
  ctr: { formula: 'clicks / impressions' },
  cpm: { formula: 'spend / impressions * 1000' },
}
```

The gateway aggregates `clicks`, `impressions` and `spend` at the requested breakdown, then applies the formula to the aggregated values and guards against a zero denominator. When the base metrics live on different tables, the same rule applies: aggregate each table at the shared breakdown first, then combine. That is a CTE per table and a join on the breakdown keys, which is the standard star-join the gateway generates for tier 2 when a request spans several fact tables.

## The escape hatch: CTE and template queries

Some questions do not fit metrics and breakdowns: a ranked leaderboard with business rules, a unique-reach count over a window, a report that must drop low-volume rows before ranking. Forcing these into the metric model makes the model worse. The escape hatch is a **named, parameterized SQL template** kept in the repository.

A template engine (Jinja and Mustache are examples) renders it. The shape is one file per query, with shared rules in an included file, and the consumer sends a name and parameters, never SQL.

```sql
{% include "leaderboard/rules.sql" %}
with events as (
  select item_name, placement_id,
         sum(impressions) as impressions,
         sum(conversions) as conversions
  from ad_event_daily
  where day between :start_day and :end_day
  group by item_name, placement_id
),
eligible as (
  select * from events
  where {{ minimum_volume_rule }}
)
select item_name,
       sum(impressions) as impressions,
       sum(conversions) as conversions
from eligible
group by item_name
order by conversions desc
limit :row_limit
```

The template decides the structure, so the structure is reviewed. The parameters decide the values, so they stay bound parameters and never string concatenation. Four rules keep this safe and boring:

1. **Templates are code.** They live in the repo, go through review, and ship with the service. Nobody posts SQL to the API.
2. **Values are bound, structure is rendered.** Dates, ids and limits are bound parameters. Only fragments that come from the service's own constants, such as a shared rule, are rendered into the text.
3. **The engine is sandboxed.** Restrict what a template can reach (no reflection, no file or network classes), so a template can only produce text.
4. **Each template has a test with expected SQL.** Render it with fixed parameters and compare to a checked-in file. A change to a template shows up as a diff in review.

One trap to avoid: shared rule files grow lists of business constants (long lists of names and thresholds). Those drift. Move them into metadata as data, and let the template read them as parameters.

A template is also how you serve an old report unchanged while its pieces are moved into metrics. Migrate one CTE at a time into tier 2 and delete the template when nothing is left in it.

## How big is this, and how big can it get

Lean first, scale on demand. Each step below is added only when a measured limit appears, and none requires redesigning the layer above it.

| Stage | Add | Trigger |
|---|---|---|
| 1. Single service | one JVM or Node service, metadata in a small relational store, in-memory metadata cache reloaded on change | first consumers |
| 2. Cache | result cache keyed by the normalized request, short expiry | repeated dashboard queries |
| 3. Several engines | a driver per datasource: warehouse for history, a columnar store for fresh data | one engine cannot serve both depth and freshness |
| 4. Splitting | one request spanning two datasources is split, each part run where it lives, results merged by the shared breakdown | metrics live in different engines |
| 5. Async and paging | long queries return a job handle, large results stream | exports and wide time ranges |
| 6. Precompute | materialize the hot rollups and register them as physical metrics with higher priority | a query shape dominates cost |

Stage 6 is where the design pays off. Because consumers ask by name, adding a faster physical table changes nothing for them. The gateway just prefers it.

## Long term: reporting, serving and the feedback loop

Ads is a loop. Promotions are configured, ads are served, results are measured, and the measurement changes the next decision. If reporting and serving read different definitions of the same metric, the loop is built on two truths.

The gateway can be the single source of truth for the **control plane** of that loop, the decisions that run on seconds-to-minutes timescales: spend throttling, frequency capping, bid adjustments, alerts when spend falls behind plan. It should not sit in the **data plane**: the auction decision at request time has a latency budget a SQL gateway cannot meet. That path reads precomputed values from a low-latency store, and those values are produced from the same logical definitions.

<Workflow client:visible flow={feedbackLoopFlow} title="The feedback loop" height={380} />

Minimal-effort feedback looks like this:

- The same logical metric binds to a fresh physical table (minutes old, narrow) and a complete one (hours old, wide). Priority and a freshness requirement on the request choose between them.
- A throttling job is just another consumer. It queries served impressions against goal by placement through the same API, computes the adjustment, and writes it to the system that serves ads.
- Because the job asks by name, a table move or a new engine behind the metric never touches it.

What the gateway does not do is write back or decide. It stays a read layer with one set of definitions, and the feedback loop is built from consumers of that layer.

## How others do it

The reasoning is not new. Each of these systems takes a different position on how much the consumer says and how much the service decides. Every claim below is from the system's own documentation, retrieved 2026-11-22 or 2026-11-23; follow the links.

| System | Consumer asks | The service decides |
|---|---|---|
| [Google Ads reporting](https://developers.google.com/google-ads/api/docs/query/overview) | a query in GAQL: `SELECT` metrics and segments `FROM` one resource | which combinations are legal, using a compatibility list per segment; related resources join implicitly when you select from them |
| [Meta Marketing API insights](https://developers.facebook.com/docs/marketing-api/insights/breakdowns) | requested metrics, breakdowns and a time range at an object level (account, campaign, ad set, ad) | which breakdown permutations exist: "only some permutations of breakdowns are available" |
| [Uber data abstraction layer](https://www.uber.com/blog/data-abstraction-layer/) | a request against logical tables, first used for advertiser reporting | which physical table answers it, chosen in phases; joins are applied while assembling the result |
| [DataJunction](https://github.com/DataJunction/dj) | metrics and dimensions defined in SQL on a node graph | join paths inferred from dimension links |
| [dbt MetricFlow](https://docs.getdbt.com/docs/build/join-logic) | metrics and dimensions | joins by entity type, with fan-out and chasm joins restricted, and at most two hops |
| [Cube](https://docs.cube.dev/docs/data-modeling/concepts/working-with-joins) | measures and dimensions from a view | joins declared with a relationship; a view fixes the join path to remove ambiguity |

What to take from this:

- **Google Ads and Meta both expose the same idea to ad buyers**: name metrics and breakdowns, and the platform decides what combinations are valid. Google exposes the rules as metadata you can query (`selectable_with`), and Meta states the limit in prose. Both show that a restricted, well-described combination space is a feature, not a gap.
- **Meta separates the quick and the slow path**: a synchronous request, and an asynchronous report job you poll and then fetch. That is stage 5 above.
- **Uber's layer is the closest in shape** to the one described here, with logical tables, several physical candidates per metric and staged table selection. The post does not describe declared join costs.
- **MetricFlow restricts fan-out** by type. This design ranks routes by declared cost and uses fan-out as a tie-break, which allows more routes at the price of more configuration.
- **Cube fixes the path in the view.** That makes results predictable and takes the search away. It is the right call when the model is small.

DataJunction is often associated with Netflix, but its own README and site do not say so, so I list it by name only. I also did not retrieve Airbnb's Minerva posts, so it is not compared here.

## When not to build this

- **One consumer, one warehouse.** A few well-named curated tables in the warehouse are enough.
- **A BI tool already holds your definitions** and every consumer is that tool. Use its model.
- **Definitions change daily and nobody owns them.** A central service freezes the disagreement instead of resolving it. Fix ownership first.
- **The data is one wide table.** There is no join to find.

Build it when several consumers need the same numbers, the tables are many and the joins are easy to get wrong. Start with tier 1 and 2, add tier 3 when ratios appear, keep tier 4 as the exception, and let scale arrive in the order of the table above.
