Ask three teams for last month's revenue and you can get three answers. Each team wrote its own query. One joined a table at the wrong level of detail, one counted a row twice, one filtered out something the others kept. Nobody was careless. The definition of the number simply lived in many places, so it drifted.

A semantic layer is the response. It holds the shared, governed definitions of metrics and dimensions between the people asking questions and the databases that hold the data. A consumer asks in business terms, and the layer writes the SQL. The rest of this post explains why that is worth doing, how the request becomes a query, how the idea compares with systems that other teams have documented, and when you should not build one.

The examples use an invented ad-reporting world, so every idea can be read without any knowledge of a real schema.

## What goes wrong without one

Three problems recur when every consumer writes its own SQL.

- **The definition is copied, so it diverges.** A metric is a rule: which rows count, how they are aggregated, what is excluded. Copy the rule into a dashboard, a notebook and a scheduled report, and the first change reaches only one of them.
- **Joins are easy to get wrong.** Reaching an attribute often takes a chain of joins through several tables. A join where one row on the near side matches many rows on the far side is a fan-out, and it silently counts measures from the near side more than once. The query still runs. The number is just wrong.
- **Storage leaks into questions.** The same measure may exist in a fine-grained table and in a pre-aggregated one, in different engines. Consumers end up choosing tables by hand, and every migration breaks someone.

A semantic layer attacks all three by moving the rule, the join choice and the table choice out of the consumer's query and into shared metadata.

## From a request to SQL

The layer has to turn a request in business terms into one correct query. The pipeline below is the whole idea in five steps. Select a step, or press Play to walk through it.

Each step answers one question.

1. **Request.** The consumer names a logical metric, some logical dimensions and filters. A logical metric is a business-named measure that does not depend on where it is stored. A logical dimension is a business-named attribute used to slice or filter, with a data type and a grain.
2. **Resolve.** The layer looks up which physical metrics and physical dimensions can answer. A physical metric is a logical metric bound to a column of a specific table, with an aggregation and a priority. A physical dimension is the same binding for a dimension. Several bindings can exist for one logical name, which is how the same measure can live in more than one place.
3. **Choose a table.** Grain orders tables and dimensions from fine to coarse detail. A metric table can be broken down only by dimensions at its own grain or coarser, so a request for a fine breakdown of a coarse table is rejected rather than answered with a wrong number. A virtual table is a registered view of a table that states which metrics, breakdowns and filters it can answer, and the layer picks one that fits.
4. **Find a route.** Join rules connect the chosen table to each dimension table. A join rule is a declared connection between two tables, with a cost, a cardinality and an on-off switch. The route is the chosen sequence of joins. It is picked by cost, with fan-out as a tie-break, and a role lets the same table appear twice in a route, for example a billing agency and a buying agency that are both rows of one agency table. The route search is the subject of [a later post](../finding-the-join/), where you can step through it.
5. **Generate SQL.** The chosen tables and route become one query in the dialect of the engine that holds the data. When a request cannot be resolved, the layer answers with a reason that says which step failed, so the author of the request can fix it.

Finding a route does not have to be a single method. A strategy ladder orders the ways of trying: an explicit rule for a dimension first, then a declared multi-hop route, then a rule over several columns, and last a join inferred from a shared dimension. Explicit statements win over inference, and inference is the fallback.

The split between logical and physical definitions is covered in [the next post](../logical-versus-physical-model/), and the way the pieces fit into a running service in [the last one](../building-the-platform/).

## How other teams approach it

The idea is not new, and several teams have written about their own versions. The notes below use only claims that can be checked against each system's own documentation or engineering posts. Each claim links its source, retrieved on 2026-11-22. A statement that a page does not describe something means only that the cited page did not describe it on that date. It is not a claim that the system lacks the feature.

**A metrics platform built on a graph of nodes.** DataJunction describes itself as [a semantic layer on top of a physical data warehouse](https://github.com/DataJunction/dj), where metrics and the logic behind them are stored as connected nodes. A dimension is linked to another node by a join link with an explicit condition and join type, or by a reference link that maps a column directly and performs no join, as described in its [dimension links documentation](https://datajunction.io/docs/0.1.0/data-modeling/dimension-links/). It also has a role concept for one dimension attached in two capacities, which serves the same purpose as a role here. The pages read do not show a cost or a cardinality on a link, and do not describe how one path is picked among several.

**A semantic graph with admissibility rules.** MetricFlow models data as [semantic models connected by entities](https://docs.getdbt.com/docs/build/semantic-models), and its [join logic](https://docs.getdbt.com/docs/build/join-logic) builds a graph from them to perform joins automatically. Whether two entities may be joined depends on their types, and pairings that would fan out are listed as not allowed. Multi-hop joins are limited to a short fixed number of hops, and validation runs before execution and checks for ambiguous paths. Here cardinality decides what is admissible, whereas in the design described in this series it is declared on the join rule and cost decides among admissible routes. The pages read show no declared cost.

**Cubes with explicit paths.** Cube declares [joins inside a cube with a declared cardinality](https://docs.cube.dev/docs/data-modeling/concepts/working-with-joins) and states that all joins are directed. When more than one path exists between two cubes, the same page says it can lead to ambiguous query generation, and the author resolves it by writing an explicit path in a curated layer above the cubes. That is predictable, because the author decides every route, at the price of writing each one. The pages read do not describe how a path is chosen when no such layer is used.

**Explores with symmetric aggregates.** LookML fixes the join structure when the model is written: an [explore declares its joins](https://docs.cloud.google.com/looker/docs/reference/param-explore-join), each with a cardinality and a join type, and the same table can be joined more than once. For fan-out it corrects the aggregate instead of avoiding the join, using [symmetric aggregates](https://docs.cloud.google.com/looker/docs/best-practices/understanding-symmetric-aggregates) so that sums and counts stay correct when a join duplicates rows. That depends on a unique primary key and a correctly declared join cardinality.

**A data abstraction layer between consumers and producers.** Uber describes [a service between data consumers and data producers](https://www.uber.com/blog/data-abstraction-layer/) that decides where to source data. Logical tables describe the shape of the data without saying where it lives, each metric has candidate physical tables, and routing resolves a table in phases. The post does not give explicit criteria for choosing joins. Its earlier [metric platform post](https://www.uber.com/blog/umetric/) separates a view definition, a metric definition and runtime dimensions and filters.

Read together, the sources agree on the shape: shared definitions, a separation between business names and storage, and some answer to the join problem. They differ on how much the author decides and how much the system searches for. Cube puts the choice in the author's hands, LookML corrects for the consequences of a join, and MetricFlow restricts what may be joined. The design in this series searches, ordering routes by declared cost and using fan-out to break ties, and it reports a reason when nothing resolves.

## Pros and cons

| | Advantage | Cost |
|---|---|---|
| Definitions | One governed place for each metric, so numbers agree across tools | Every definition needs an owner and a review process |
| Joins | Consumers stop writing joins, and fan-out is handled once | The join metadata must be declared and kept correct |
| Storage | Tables and engines can change without breaking questions | An extra layer to operate, and one more thing between a question and the data |
| Access | One place to apply permissions and audit use | A new single point whose outage stops every consumer |
| Flexibility | Many consumers share one vocabulary | Requests outside the modelled vocabulary need the model to grow first |
| Explainability | A failed request returns a reason | Someone has to write those reasons well |

## When not to build one

A semantic layer is infrastructure, and infrastructure has a carrying cost. Skip it, or postpone it, in these cases.

- **Few consumers and few metrics.** If one team writes all the queries and the definitions fit in a short document, one shared, saved query in the database does the same job for far less.
- **Exploratory work.** When questions change daily and nothing needs to agree with anything else, a governed vocabulary slows people down.
- **No owner.** A layer whose definitions nobody maintains drifts exactly like the copied queries it replaced, and it adds a place to look.
- **A single engine with a good modelling tool already in place.** If the tool you have already gives governed metrics for the consumers you have, adding a second layer duplicates it.
- **Data that is not yet trustworthy.** A semantic layer organizes definitions. It does not repair the tables beneath it, and it will serve their errors consistently.

The test is whether the cost of disagreement is higher than the cost of governance. When two teams argue about a number every month, it usually is.

## What it costs

The honest cost is the metadata. Join rules need costs and cardinalities, logical names need bindings, and every change needs review. A layer that is only half modelled is worse than none, because consumers trust it and it answers some questions incorrectly and others not at all. Plan for the model to be a product with an owner, and expect most of the effort to go into keeping the declarations true.
