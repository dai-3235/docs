A semantic query gateway receives a request for a metric broken down by a dimension, and the two often live in tables that are not directly joined. Something has to decide which joins connect them, and a poor choice either costs more than it should or counts the same measure more than once.

The demo below uses an invented ad-reporting schema. Pick a scenario, press Step or Play, and watch the route grow one join at a time, with the running cost and the number of fan-outs beside each step.

## How a route is chosen

Every join rule declares a cost, a cardinality and an on-off switch. The search settles on the route that wins on these, in order:

- **Lowest total cost.** A shortcut with one join loses to a longer chain that costs less.
- **Fewest fan-outs.** When two routes cost the same, the one that multiplies fewer rows wins, because fan-out is what inflates measures.
- **Fewest joins.** The last tie-break, so equal routes resolve to the simpler one.

Rules that are switched off are skipped entirely, and a hop limit caps how many joins a route may use, even when a longer route would be cheaper.

## One table, two roles

The same table can appear in a route twice when it plays different roles, such as a buying agency and a billing agency. The search tracks each role separately, so reaching the table under a second role is not treated as going in a circle.

> [!NOTE]
> Cost and fan-out are separate on purpose. Cost expresses preference between valid routes. Fan-out is a correctness risk that cost alone would hide.

## What it costs

Costs are declared by hand, so a route is only as good as the numbers behind it. The search is exhaustive within the hop limit, which is fine for a schema of this size and is a trade-off for a much larger one.
